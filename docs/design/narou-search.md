# 設計メモ：なろう小説検索システム（中間課題）

- 作成日：2026-10-27
- 元にしたシステム：https://github.com/Yuu0413s/book_recom_web（React + Cloudflare Workers / D1 / Vectorize）
- 公開先：https://muds.gdl.jp/s2422016/
- 作業フォルダ：`mid_assign/`（サーバの `~/myapp/` にアップロード）

---

## 1. 目的

「小説家になろう」の作品データを自前の DB に保存し、それをもとにキーワード・作者・ジャンルで作品を検索できる Web アプリを Flask で作り、授業サーバで公開する（専門デプロイメントⅢの中間課題）。

- 課題の要件は「Web システムを開発すること」のみ（必須機能の指定なし）

## 2. ユーザー

| 誰が | 何をする | ログイン |
|---|---|---|
| 閲覧者（誰でも） | 小説を検索して結果を見る | 不要 |
| 管理者（自分 1 人だけ） | 管理画面からなろう API のデータを DB に取り込む | 必要 |

- 管理者アカウントは `create_admin.py` で作り、運用として 1 人だけにする（スクリプト自体は、別のユーザー名なら何人でも作れる）。**登録画面は作らない**（公開すると誰でも管理者になれるため）
- パスワードは Werkzeug の `generate_password_hash` / `check_password_hash` で保存・照合する（ソルト付きで総当たりされにくい。week03 の `sha512` はソルトが無いので使わない）
- **サイト全体**を https へ強制リダイレクトする（http だとパスワードや session の Cookie が平文で送られるため）。`SESSION_COOKIE_SECURE` が True の環境（サーバ）だけ切り替え、ローカルの http では切り替えない

## 3. 課題

1. 元のシステムは React + Cloudflare で作られており、授業サーバでは動かせない。授業サーバで動く形で作り直す必要がある
2. なろう API を検索のたびに呼ぶと、遅い・API に負荷をかける・検索条件が API の仕様に縛られる
   → **データを一度 DB に取り込み、検索は自分の DB だけで行う**ことで解決する

### 元のシステムからの作り直しの範囲

| 元のシステム | 今回 | 扱い |
|---|---|---|
| React + Yamada UI | Flask テンプレート（Jinja2） | 作り直し（画面構成・文言は参考にする） |
| Workers / Hono | Flask のルート | 作り直し |
| D1（SQLite） | PostgreSQL | テーブル設計の考え方を流用 |
| なろう API の取得処理 | `requests` | 流用（パラメータを追加） |
| Google Books / Open Library / 青空文庫 / CiNii | ― | 作らない |
| Vectorize + Gemini（AI 推薦） | Gemini 埋め込み API + PostgreSQL の配列 + Python での類似度計算 | MVP 後に追加（§11） |

## 4. 機能

### MVP に含める

| # | 機能 | 使う人 |
|---|---|---|
| 1 | キーワード検索（タイトル・あらすじ・キーワード（タグ）のどれかに部分一致） | 閲覧者 |
| 2 | 作者名で検索（部分一致。1 と組み合わせ可） | 閲覧者 |
| 3 | ジャンル絞り込み（大ジャンルごとに見出しを付けたプルダウン） | 閲覧者 |
| 4 | 並び替え：総合ポイント順（初期値）/ ブックマーク数順 / 最終更新日順（新しい順） | 閲覧者 |
| 5 | 検索結果の一覧（20 件ごとにページ分け。タイトル・作者・ジャンル・あらすじ・最終更新日を表示。なろうの作品ページへのリンク付き） | 閲覧者 |
| 6 | 管理者ログイン / ログアウト | 管理者 |
| 7 | 取り込み（下記） | 管理者 |

### 取り込みの仕様

- なろう API から **総合ポイント順（`order=hyoka`）の上位 100 件** を取得する
- 新しい作品は追加し、既にある作品（同じ ncode）は上書き更新する（蓄積方式）
- **最終取得から 14 日を過ぎた作品は、取り込み時に削除する**
  - なろう API の利用ガイドラインに「保存したデータは長くても 2 週間以内に更新か削除をすること」とあるため
- 取り込みは 1 つのトランザクションで行う。途中で失敗したら全部取り消す。14 日削除も取り込みが成功したときだけ行う
- 単位 2 で決めたこと：
  - `keyword` が空文字（タグなし）のときは NULL にする
  - API の応答が 0 件・同じ ncode の重複・形式違いのときは `NarouApiError` にして、DB には何もしない
  - 追加・更新の件数は、保存前に既存の ncode を SELECT して数える。同時に取り込みが走っても件数がずれないよう、トランザクションの最初に `LOCK TABLE novels IN SHARE ROW EXCLUSIVE MODE` をかける（検索の SELECT は待たされない）
  - 取り込み時刻は `Asia/Tokyo` を明示して作る（API の日時が JST のため）
  - コマンドからも実行できる：`flask --app myapp import-novels`（サーバでは `cd ~/myapp && python3 -m flask --app myapp import-novels`）
- 補足：総合ポイント順は歴代の人気作なので、上位 100 件はほとんど変わらない。DB の作品数は 100 件前後から大きくは増えない見込み（承知のうえで採用。API の `order` を変えれば日間・週間に切り替えられる）

### MVP に含めない

| 機能 | 理由 |
|---|---|
| AI 検索（類似度・推薦） | MVP の後に追加する。設計は §11 |
| なろう以外のデータソース | 今回の目的の範囲外 |
| cron での定期的な自動取り込み | サーバで cron が使えるか不確か。手動の取り込みで足りる |
| 管理者の登録画面 | 管理者は自分 1 人だけ |
| 取り込み履歴の一覧 | 最終取り込み日時だけ表示すれば十分 |
| ログイン試行の回数制限 | 管理者 1 人のため、推測されにくいパスワードで対応 |

## 5. 画面構成

```
【閲覧者】
  検索画面  /
  ├── 検索フォーム（キーワード・作者・ジャンル・並び替え）
  └── 検索結果の一覧（20件ごと・ページ送り）
        └── タイトルをクリック → なろうの作品ページ（別タブ）

【管理者】
  ログイン画面  /admin/login
        │ ログイン成功
        ▼
  管理画面  /admin
  ├── DB の作品数・最終取り込み日時
  ├── 「取り込む」ボタン → 結果を表示（追加◯件・更新◯件・削除◯件）
  └── ログアウト → 検索画面へ
```

- 検索フォームと結果は同じ画面（元のシステムと同じ構成。結果を見ながら条件を変えやすい）
- 検索条件は URL に入れる（例：`/?q=転生&genre=201&page=2`）。ページ送りがしやすく、URL を共有できる
- 作品の詳細画面は作らない（一覧にあらすじまで表示し、続きはなろうで読む）
- 検索画面に管理画面へのリンクは置かない（管理者は `/admin` を直接入力する）
- 単位 3 で決めたこと：
  - 一覧に出す項目は **タイトル・作者・ジャンル・あらすじ・最終更新日**。タグは長くて一覧が読みにくくなるため出さない。総合ポイント・ブックマーク数は並び替えにだけ使い、表示しない
  - キーワードは空白（全角も可）で区切ると **AND 検索**（すべての語を含む作品）。各語はタイトル・あらすじ・タグのどれかに含まれればよい
  - キーワードは同じ語を 1 つにまとめたうえで **先頭 10 語まで** 使い、11 語目以降は画面に何も出さずに無視する（1 語ごとに SQL の条件が増え、語を大量に並べた URL で DB を重くされるため）
  - キーワード・作者に含まれる NUL 文字（`\x00`）は取り除く（psycopg2 が SQL に渡せずエラーになるため）
  - `%` `_` `\` は文字としてそのまま検索する（`ILIKE ... ESCAPE '\'` でエスケープ）
  - あらすじは **先頭 200 文字** まで表示し、超えたら「…」を付ける
  - ジャンルは一覧では正式名（例：ハイファンタジー〔ファンタジー〕）、プルダウンでは大ジャンルごとにまとめた短い名前で表示する。辞書に無いコードは「不明」
  - 作品数を超えたページ番号を指定されたら「このページには作品がありません」と 1 ページ目へのリンクを出す（エラーにしない）
  - 同じ値で並ぶときは `id` 順にして、ページをまたいで同じ作品が出たり抜けたりしないようにする
  - DB 接続（`get_db`）は `myapp.py` に置き、取り込みコマンドも同じ関数を使う（リスク 6 の対策）
  - ローカルの Docker の PostgreSQL もタイムゾーンを `Asia/Tokyo` にする（サーバと揃えないと `created_at` の時刻が 9 時間ずれるため）
- 単位 4 で決めたこと：
  - 管理者は `python3 create_admin.py` で作る（flask のコマンドにはしない）。ユーザー名と、パスワードを 2 回（画面に表示しない `getpass`）入力する。同じユーザー名がいればエラーで止め、既存のパスワードは変えない
  - ユーザー名の前後の空白は、作るときもログインのときも取り除く
  - ログインはブラウザを閉じるまで有効（`session.permanent` を使わない）。ただし最後に session が書き換わってから（ログイン・取り込みなど）**8 時間**たつと、ログインし直しになる（`PERMANENT_SESSION_LIFETIME`。リスク 13）。切れたあとにページを開き直せばログイン画面へ移るが、開いたままの画面で取り込み・ログアウト・ログインのボタンを押すと、CSRF トークンも消えているので 400 になる（ページを開き直せばよい）
  - ログインに失敗したら、ユーザー名・パスワードのどちらが違っても同じ文言（「ユーザー名またはパスワードが違います」）にする。ユーザーがいないときもダミーのハッシュで照合し、応答時間の差からユーザー名の有無を推測されないようにする
  - 管理画面の最終取り込み日時は `2026-10-27 12:34` の形（秒は出さない）。作品が 0 件なら「まだ取り込んでいません」
  - 取り込み結果の文言は、取り込みコマンドと同じ「追加 ◯ 件・更新 ◯ 件・削除 ◯ 件」。取り込みの処理（`run_import`）はコマンドと管理画面で共通にする

## 6. データ構造

PostgreSQL の、授業で使っている `s2422016` データベースに作る（既存の `pychat`・`flskauth` とテーブル名は重ならない）。

### `novels`（作品）

| カラム | 型 | NULL | 内容 | API の項目（`of`） |
|---|---|---|---|---|
| `id` | `SERIAL` | × | 主キー | ― |
| `ncode` | `TEXT` | × | Nコード。**UNIQUE** | `ncode`（`n`） |
| `title` | `TEXT` | × | タイトル | `title`（`t`） |
| `writer` | `TEXT` | × | 作者名 | `writer`（`w`） |
| `story` | `TEXT` | × | あらすじ | `story`（`s`） |
| `biggenre` | `INTEGER` | × | 大ジャンルのコード | `biggenre`（`bg`） |
| `genre` | `INTEGER` | × | ジャンルのコード | `genre`（`g`） |
| `keyword` | `TEXT` | ○ | キーワード（空白区切り） | `keyword`（`k`） |
| `global_point` | `INTEGER` | × | 総合ポイント | `global_point`（`gp`） |
| `fav_novel_cnt` | `INTEGER` | × | ブックマーク数 | `fav_novel_cnt`（`f`） |
| `general_lastup` | `TIMESTAMP` | × | 最終掲載日 | `general_lastup`（`gl`） |
| `fetched_at` | `TIMESTAMP` | × | 最後に API から取得した日時（14 日削除に使う） | ― |
| `created_at` | `TIMESTAMP` | × | 初めて DB に入った日時 | ― |

### `admins`（管理者）

| カラム | 型 | NULL | 内容 |
|---|---|---|---|
| `id` | `SERIAL` | × | 主キー |
| `username` | `TEXT` | × | ログイン名。UNIQUE |
| `password_hash` | `TEXT` | × | Werkzeug でハッシュ化したパスワード |
| `created_at` | `TIMESTAMP` | × | 作成日時 |

### 設計上の判断

| 判断 | 理由 |
|---|---|
| 主キーは連番の `id`、`ncode` は UNIQUE | 主キーが外部（なろう）の都合に左右されない。AI 検索用のテーブルを後で作るとき数値の `id` で結び付けられる |
| ジャンル名は Python の辞書（`genres.py`）に持つ | 約 20 種類でほぼ変わらないため、テーブルにする利点が小さい |
| カラム名はなろう API の項目名をそのまま使う | 取り込み処理で名前を変換せずに済み、対応関係を間違えない |
| `keyword` を保存し、検索対象に使う（一覧には表示しない） | タグでも検索でき、AI 検索の材料にもなる。一覧に出さない理由は §5 の単位 3 で決めたことを参照 |
| 取り込み履歴テーブルは作らない | 最終取り込み日時は `MAX(fetched_at)` で分かる |
| 上書き更新は `INSERT ... ON CONFLICT (ncode) DO UPDATE` | 「あれば更新、無ければ追加」を 1 文で書ける |
| 検索用のインデックスは張らない | 100 件前後なので `ILIKE '%…%'` の全件走査で十分速い |

## 7. API 設計

Flask が HTML を返す構成（week02・03 と同じ）。JSON の API は作らない。

### ルート一覧

| メソッド | URL | ログイン | 処理 | 返すもの |
|---|---|---|---|---|
| GET | `/` | 不要 | 検索して一覧を表示 | 検索画面 |
| GET | `/admin/login` | 不要 | ログインフォームを表示 | ログイン画面 |
| POST | `/admin/login` | 不要 | パスワードを照合 | 成功 → `/admin` へリダイレクト / 失敗 → ログイン画面にエラー表示（401） |
| GET | `/admin` | 必要 | 作品数・最終取り込み日時を表示 | 管理画面 |
| POST | `/admin/import` | 必要 | なろう API から取り込み | 成功 → `/admin` へリダイレクトし結果を表示 / 失敗 → 500 の画面 |
| POST | `/admin/logout` | 必要 | ログアウト | `/` へリダイレクト |

- ログインが必要な URL に未ログインでアクセスしたら `/admin/login` へリダイレクト
- ログイン済みで `/admin/login` を開いたら `/admin` へリダイレクト
- POST はすべて CSRF トークンを確かめ、無いか違えば 400

### `/` の検索パラメータ

| パラメータ | 意味 | 不正な値のとき |
|---|---|---|
| `q` | キーワード（タイトル・あらすじ・タグの部分一致） | NUL 文字は取り除く。11 語目以降は無視 |
| `writer` | 作者名（部分一致） | NUL 文字は取り除く |
| `genre` | ジャンルのコード | 無視（全ジャンル） |
| `sort` | `point`（初期値）/ `fav` / `lastup` | `point` |
| `page` | ページ番号（初期値 1、1 ページ 20 件） | 1 |

### 設計上の判断

| 判断 | 理由 |
|---|---|
| 取り込み・ログアウトは POST | GET だとリンクを踏ませるだけで実行させられるため |
| 取り込み後は `/admin` へリダイレクト（PRG パターン） | 結果画面で更新ボタンを押しても取り込みが再実行されないようにするため |
| CSRF トークンを自前で実装する | サーバに Flask-WTF が無い。管理者の POST（ログイン・取り込み・ログアウト）を守るため |
| ログイン管理は `session` で自前実装 | サーバに Flask-Login が無いため（week03 と同じ方式） |
| ログインに成功したら `session` を作り直す | ログイン前の `session`（攻撃者が用意したものかもしれない）を引き継がないため（session 固定攻撃の対策）。CSRF トークンも作り直される |
| Cookie に `SameSite=Lax` を明示する | ほかのサイトからの POST に Cookie を送らないようにし、CSRF トークンと二重に守るため |
| https への切り替えは 302 | 301 はブラウザに記憶され、設定を戻しても切り替わり続けるため |
| パスワードのハッシュは `scrypt` と明示する | Werkzeug の既定に任せると、更新したときに方式が黙って変わるため |
| 取り込みの失敗（なろう API・DB）は 500 の画面にする | 失敗はまれで、管理者は自分だけなのでエラーログで原因を見れば足りるため。なろう API のエラーの文言には、自分で書いた説明・requests の例外の文言（API の URL）・API の応答の値が入る。どれも公開されている値で秘密を含まないので、そのままログに出す |
| DB のエラーは種類名だけをログに出し、500 の画面を返す | 例外の文言に接続先や接続文字列の一部が含まれることがあり、エラーログはほかの学生も読めるため |
| 不正な検索パラメータは初期値に置き換える | 誰でも使う画面なので、打ち間違いでエラー画面を出さないため |
| 利用者の入力は必ずプレースホルダで SQL に渡す（SQL 文に埋め込むのはコード内の固定の文字列だけ） | week02・03 の `'%s' % 値` の書き方は SQL インジェクションを防げないため |

### デプロイ・管理の方針

| 判断 | 理由 |
|---|---|
| Flask（mod_wsgi・`~/myapp/`）を使う。CGI にしない | `~/myapp/` は公開フォルダの外なので秘密情報を Web から読まれない。授業内容に沿う |
| sftp.json に「mid_assign → `/home/s2422016/myapp`」の設定を追加する | 保存時の自動アップロードを保ったまま、送り先を確実に `~/myapp/` にできる。`~/myapp/` も最初のアップロードで自動作成される |
| ファイルは役割ごとに分ける（Blueprint は使わない） | 1 ファイルが短く、読む場所がすぐ分かる。画面 3 つの規模に Blueprint は大げさ |

## 11. AI 検索（MVP の後に追加）

§1〜10 の MVP が完成したあとに追加する機能。§10 リスク 12 の調査結果（上の参考）をもとに設計した。

### 11.1 目的

キーワードが一致しなくても、「読みたい話の内容」を文章で入力すれば、意味の近いなろう作品が見つかるようにする。あわせて、元のシステムの AI 推薦（Gemini + Vectorize）を、授業サーバの制約（pgvector も numpy も無い）の中で作り直す。

### 11.2 ユーザー

| 誰が | 何をする | ログイン |
|---|---|---|
| 閲覧者（誰でも） | 文章を入力して AI 検索し、意味の近い作品を見る。作品ごとに「似ている作品」を見る | 不要 |
| 管理者（自分 1 人） | 取り込みのときに、作品のベクトル化も一緒に行う。足りない分をベクトル化し直す | 必要 |

- 作品のベクトル化（API を呼ぶ）は管理者の操作でだけ行う。閲覧者の AI 検索では、入力した文章の変換で API を 1 回呼ぶ（リスク 19）

### 11.3 課題

- キーワード検索は「入力した語がそのまま含まれるか」しか見ないので、言い換えに弱い（「追放」で探すと「パーティーを抜けさせられた」とだけ書いた作品が出ない）
- 読みたい話の雰囲気（「ほのぼのしたスローライフ」など）を表す語が分からないと探せない
- 語を AND でつなぐと、条件を細かく書くほど結果が 0 件に近づく
- 作品名・作者名で探す、ジャンルで絞るといった、はっきりした条件の検索は、引き続きキーワード検索を使う

### 11.4 機能

**含める**

| # | 機能 | 使う人 |
|---|---|---|
| 1 | 作品のベクトル化：取り込みのときに、タイトル・あらすじ・タグを 1 つの文章にして Gemini でベクトルにし、保存する | 管理者（取り込みと一緒に自動で） |
| 2 | 足りない分のベクトル化：ベクトルが無い・古い作品だけを変換し直す | 管理者 |
| 3 | 管理画面に、ベクトル化の状況を表示する（例：「100 件中 98 件」） | 管理者 |
| 4 | AI 検索：文章を入力すると、意味の近い順に上位 20 件を表示する | 閲覧者 |
| 5 | 似ている作品：作品ごとに、ベクトルが近い作品を 20 件表示する（API は呼ばない） | 閲覧者 |
| 6 | 類似度の表示：パーセントで表示し、「数字が大きいほど内容が近い（目安）」と添える | 閲覧者 |
| 7 | 入力の制限：空の入力は検索しない。200 文字を超えたら検索せず、注意を出す | 閲覧者 |

**含めない**

| 機能 | 理由 |
|---|---|
| AI 検索の結果のページ送り | 上位 20 件で十分 |
| ジャンルなどでの絞り込みとの組み合わせ | 画面と処理を単純にするため。絞り込んだ結果が少ないと、似ていない作品まで上位に出る |
| キーワード検索との組み合わせ（ハイブリッド検索） | まず AI 検索だけで完成させる |
| 検索回数の制限・検索結果の使い回し | リスク 19 で受け入れ |

### 11.5 画面構成

```
【閲覧者】
  検索画面  /
  ├── 切り替えのタブ［キーワード検索］［AI 検索］（リンク。JavaScript は使わない）
  ├── キーワード検索のとき（/?q=…）：今のまま
  └── AI 検索のとき（/?mode=ai&q=…）
        フォーム（文章の入力欄だけ）→ 意味の近い順に上位 20 件（ページ送りなし）
        └── 各作品：同じカード ＋「類似度 82%」＋「似ている作品」リンク

  似ている作品の画面  /novels/<ncode>/similar
  ├── 元の作品
  └── 近い順に 20 件（同じカード ＋ 類似度）

【管理者】
  管理画面  /admin  ＋ ベクトル化の状況・「足りない分をベクトル化」ボタン
```

- タブはモードごとにフォームを出し分ける。AI のときは作者・ジャンル・並び順の欄を出さない（入れても効かない欄を見せないため）。タブを切り替えても、入力中の文章は引き継がない
- 作品のカードは、キーワード検索・AI 検索・似ている作品で同じ部品（`_novel_card.html`）を使う
- 「似ている作品」のリンクは、キーワード検索と AI 検索の両方のカードに付ける（作品の詳細画面が無いため）
- パーセント表示は、関係の薄い文章どうしでも 60% 前後になりやすい（不確か）ので、目安である旨を添える（リスク 25）

### 11.6 データ構造

#### `novel_embeddings`（作品のベクトル）

| カラム | 型 | NULL | 説明 |
|---|---|---|---|
| `novel_id` | `INTEGER` | × | 主キー。`novels.id` を参照（`ON DELETE CASCADE`） |
| `embedding` | `REAL[]` | × | ベクトル（768 個の数） |
| `model` | `TEXT` | × | 変換に使ったモデル名と次元数（例：`gemini-embedding-2:768`。`gemini.EMBEDDING_ID`） |
| `source_hash` | `TEXT` | × | 変換した文章（タイトル・あらすじ・タグ）のハッシュ |
| `updated_at` | `TIMESTAMP` | × | 最後に変換した日時 |

| 判断 | 理由 |
|---|---|
| `novels` の列ではなく、別のテーブルにする | 作品の情報と AI 用の派生データを分けるため。作品が消えれば一緒に消え、ベクトル化に失敗しても作品の取り込みに影響しない。ベクトルが無い作品は、行が無いことで分かる |
| 型は `REAL[]`（4 バイトの小数の配列） | psycopg2 が Python の数のリストとそのまま行き来させてくれる。1 件あたり約 3KB で、検索の精度には十分。`DOUBLE PRECISION[]` は大きさが 2 倍で結果はほぼ変わらず、`JSONB` は数として扱うのに変換が要る |
| 取り込みのたびに、ベクトルが無い・`source_hash` が違う・`model` が違う作品だけを変換する | 毎回全作品を変換すると、取り込みのたびに作品の数だけ API を呼ぶことになり、無料枠の回数制限に引っかかりやすい |

### 11.7 API 設計

#### ルート一覧（追加・変更分）

| メソッド | URL | ログイン | 処理 | 返すもの |
|---|---|---|---|---|
| GET | `/?mode=ai&q=…` | 不要 | 入力した文章を Gemini でベクトルにし、全作品と比べて上位 20 件 | 検索画面（AI モード）。Gemini が失敗したら案内を出して 503 |
| GET | `/novels/<ncode>/similar` | 不要 | 保存済みのベクトル同士を比べて上位 20 件（API は呼ばない） | 似ている作品の画面。作品が無ければ 404 |
| POST | `/admin/embed` | 必要 | ベクトルが無い・古い作品だけを変換する | `/admin` へリダイレクトし、結果を表示（PRG） |
| POST | `/admin/import` | 必要 | **変更**：取り込みのあとに、続けてベクトル化も行う | 今と同じ。ベクトル化に失敗した件数も結果に出す |

- 取り込みコマンド（`import-novels`）も、同じくベクトル化まで行う。ベクトル化に失敗しても、取り込みが成功していれば終了コードは 0
- ベクトル化だけを行うコマンド（`embed-novels`）も用意する（`/admin/embed` と同じ処理）。失敗が 1 件でもあれば終了コードは 1
- ベクトル化は 100 件ずつ送り、送るたびに保存する。Gemini で失敗したら（回数制限に限らず）そこで止め、残りは失敗として数える（失敗の多くはキーの間違いや通信の問題で、続けても同じように失敗し、無料枠を無駄に使うため）
- `GEMINI_API_KEY` が設定に無いときも、取り込みは止めない（ベクトル化の失敗として数える）
- 結果の表示は、取り込みの行とは別の行にする：「ベクトル化しました（成功 98 件・失敗 2 件）」。失敗があるときだけ、回数制限なら「1 分ほど待ってから『足りない分をベクトル化』でやり直してください」、それ以外なら「詳しくはエラーログを見てください」の行を足す。理由の詳しい文言は、管理画面には出さずエラーログにだけ残す（コマンドでは端末に出す）
- ベクトルがまだ無い作品は、AI 検索と「似ている作品」の対象外。対象が 0 件なら「AI 検索の準備ができていません」と表示する。元の作品にベクトルが無いときの「似ている作品」も同じ

#### `/` の検索パラメータ（追加分）

| パラメータ | 意味 | 不正な値のとき |
|---|---|---|
| `mode` | `ai` なら AI 検索。それ以外・無しはキーワード検索 | キーワード検索 |
| `q`（AI モード） | 読みたい話の文章（最大 200 文字） | 空なら検索しない。200 文字を超えたら検索せず「200 文字以内で入力してください」と出す |

#### Gemini API の呼び方

- モデルは `gemini-embedding-2`、次元数は 768（`embedContentConfig.outputDimensionality`）。768 にしても、長さ 1 にそろえた値が返る
- 作品：まとめて変換する API（`batchEmbedContents`）で 100 件ずつ送る。応答は `embeddings[].values`（送った順）
- 検索の文章：1 件ずつ変換する（`embedContent`）。応答は `embedding.values`
- 用途の指定：`gemini-embedding-2` は `task_type` を使えないので、文章の先頭に決まった書き方を付ける
  - 作品（検索される側）：`title: {タイトル} | text: {あらすじ}`（タグがあれば、あらすじの後ろに改行して続ける。タイトルが空なら Gemini の説明に合わせて `title: none`）
  - 検索の文章（検索する側）：`task: search result | query: {入力した文章}`
- 無料枠は **1 分あたり 100 件**。まとめて送っても 1 件ずつ数える。枠を超えると 429 が返るので、そこで止めて、残りは失敗として数える（「足りない分をベクトル化」でやり直す）
- API キーは `instance/config.py` の `GEMINI_API_KEY` に置き、**URL ではなくヘッダー（`x-goog-api-key`）で送る**
- タイムアウトを設定する。検索のたびに呼ぶ 1 件は利用者を待たせすぎないよう 10 秒、作品をまとめて送るほうは 30 秒（なろう API と同じ）

#### 設計上の判断

| 判断 | 理由 |
|---|---|
| AI 検索は、今の検索画面のタブ（`/?mode=ai`）にする | 入口を 1 つにするため。タブでフォームを出し分けて、AI のときに使えない欄を見せない |
| API キーはヘッダーで送る | requests の例外の文言には URL が入り、エラーログ（ほかの学生も読める）にそのまま出るため。元のシステムの `?key=` は使わない |
| 取り込みのときのベクトル化の失敗は、取り込みを失敗にしない | 失敗した分は「足りない分をベクトル化」でやり直せる。Gemini の不調で、なろうの取り込み（キーワード検索）まで止めないため |
| AI 検索で Gemini が失敗したら、検索画面に「AI 検索が一時的に使えません。キーワード検索をお使いください」と出して 503 | 誰でも使う画面なので、エラー画面だけを出すより次の行動を案内するため。503 は「一時的に使えない」の意味 |
| 入力は 200 文字まで。超えたら検索せずに注意を出す | 読みたい話を 1〜2 文で書くには十分。長い入力で API の利用量を増やされないため |

### 11.11 単位0 で確認した事実（2026-10-28）

- モデル：`gemini-embedding-2`（安定版、2026 年 4 月更新、入力は最大 8,192 トークン）と `gemini-embedding-001`（2028-05-14 に提供終了の予定）。`gemini-embedding-2` は `task_type` を使えず、文章の先頭の書き方で用途を指定する
- 料金：`gemini-embedding-2` は無料枠あり。有料なら 100 万トークンあたり $0.20
- 無料枠の制限：1 分あたり 100 件（`embed_content_free_tier_requests`）。まとめて送っても 1 件ずつ数える。1 日あたりの上限はドキュメントに無く、AI Studio の画面でしか見られない
- 呼び出しの結果（ローカルから、作品 100 件）：
  - 1 件の変換：約 0.5 秒。768 次元で、長さ 1 にそろった値が返る
  - 100 件のまとめての変換：約 4.8 秒、約 3.1 万トークン
  - 検索 1 回：API が 0.45〜0.9 秒、Python での類似度の計算が約 18 ミリ秒
  - 類似度：上位で 0.73〜0.79、最下位で 0.56〜0.61
- 日本語での精度（上位 3 件）：
  - 「悪役令嬢が破滅を回避しようとする」→ 破滅フラグの悪役令嬢もの 2 件と、タイトルに「悪役令嬢」が無い同じ筋の作品
  - 「ほのぼのしたスローライフ」→「スローライフ」を含む作品と、「のんびり」と書かれた作品 2 件
- mod_wsgi からの外部への通信：2026-10-27 21:42:45 の管理画面からの取り込みが 302（成功）
